01 · 电商内部 WEB 系统 / 团队协作交付

多仓库存查询系统

查清商城与库存后台的口径冲突，
和团队落地内部多仓查询系统。

项目概览

跨境电商业务中，线上商城反复出现「前台显示有货、客户下单后后台发不出」的库存异常。我逐项核对线上商城（Shopify，负责对外销售展示）与多仓库存后台（Cin7 Omni，负责分仓库存与 ERP 履约）的订单流和接口字段，定位出前台展示与后台扣减的口径冲突，随后与团队共同交付了内部多仓库存查询 Web 系统，统一各分仓真实库存口径，替代人工跨后台核对。

统一多仓真实库存查询，消除人工来回切后台核对

01 · 业务问题

前台看着有货，仓库却发不出去。

日常运营里经常撞见同一个怪象：线上商城（Shopify）的商品页明明显示可买，客人付完款，订单进了库存后台（Cin7 Omni，多仓 ERP 系统）却卡在待发货——所属发货仓根本没货。仓库和运营每天都要在两个后台之间来回切窗口，按 SKU 和订单号一条条人工对账。

团队一开始的诉求很笼统：「能不能按全仓总库存直接卖货？」但我拿真实异常订单顺着系统查下去，发现这句诉求里其实混着两件完全不同的事：前台按什么口径展示可售库存，以及后台按什么规则决定由哪个仓履约。

02 · 根因定位

展示读的是全仓合计，履约只扣所属分支仓。

线上商城展示（Shopify） All Branches

汇总所有分仓库存后对外展示

≠
库存后台履约（Cin7） Order Branch

只从订单归属的单一分支仓扣减

核对订单流、仓库映射关系和库存字段后，根因一目了然：线上商城读取的是跨仓汇总数，但库存后台并不会因为 A 仓没货就自动从 B 仓发货；同时部分商品存在跨店仓库映射遗漏，以及相同 SKU / 条码触发自动匹配覆盖手工映射的问题。

先把「多仓合计可见」和「单仓实际可发」拆成两个清晰口径，系统设计才不会沿着错误前提越改越乱。

03 · 接口核验

返回 200 成功，不代表库存字段真的生效了。

在讨论方案时，曾有设想通过库存后台的调整接口（Adjustments）直接把库存标成「在途占用」来规避错卖。我没有直接拍板，而是先拿测试数据实测写入，并把写入后的记录重新读回比对：

写入请求 holdingQty = 1

尝试经调整接口改写在途量

→
接口回执 返回创建成功

HTTP 请求无报错

→
读回比对 holdingQty = 0

实际在途字段未被修改

和 Cin7 官方技术支持交叉确认后坐实了底层规则：holdingQty 不能通过库存调整接口直接改写，只有真实创建并发运仓间调货单（Branch Transfers），系统才会把发出仓可用量转入在途。这一步直接帮团队排除了错误的接口改造路线，避免白费开发工期。

04 · 系统落地

把多仓真实口径收进内部 Web 查询系统。

摸清两套系统的边界、补齐跨店仓库映射异常后，我与团队共同推动并交付了内部多仓库存查询 Web 系统，把运营和仓库每天高频核对的场景收进同一个页面：

  • 多维度实时查询 支持按 SKU、商品、订单号或箱标直接查询，不再在商城后台和 ERP 之间反复切换。
  • 统一分仓真实口径 明确区分「全仓汇总」与「各分仓实际可发库存」，一眼看出哪些订单当前可满足、哪些需要仓间调货。
  • 衔接到盘点与调货 在同一工作台内支持按仓库、库位和货架筛选盘点范围，让系统账面与线下货位保持一致。

我在团队中的贡献

从异常订单切入排查，核对商城与 ERP 仓库映射及接口读回行为，对齐跨部门业务口径，把排障结论沉淀为内部系统的查询与筛查规则，并全程跟进交付落地。

业务价值

原本需要人工逐单跨后台核对的库存状态，改为在内部系统按统一口径集中筛查，减少因口径打架导致的超卖沟通和仓库返工。
